# WebRTC Session Lifecycle

This document covers how viewer and monitor establish, maintain, and tear down WebRTC connections. Signal kind numbers and encryption are defined in [signal-exchange.md](signal-exchange.md). Data channel message types and segment transfer protocol are defined in [webrtc-data-channel.md](webrtc-data-channel.md). ICE/SDP/STUN configuration is defined in [webrtc-peer.md](webrtc-peer.md).

---

## Session Model

Each (viewer, monitor) device pair has at most one active `RTCPeerConnection` at a time. Mode (`'data'` or `'live'`) is declared in the initial offer-request and determines whether media tracks are added during setup.

- Viewer stores sessions keyed by `contactId`.
- Monitor stores sessions keyed by `contactId`.
- Both sides match signals to sessions by `sessionId` — a UUID generated by the viewer and echoed in every subsequent signal.

---

## Signal Router

The routing dispatch table is in [signal-exchange.md](signal-exchange.md) § Signal Router. Subscription mechanics are in [webrtc-peer.md](webrtc-peer.md). Neither the viewer-peer module nor the monitor-peer module opens its own subscription — all incoming signals arrive through the single router.

---

## Viewer-Side Session State

Viewer sessions are keyed by `contactId`. The behavioral invariants that govern the connection flows are:

- A second call to `connectToMonitor()` for the same contact returns the same in-flight Promise rather than starting a parallel handshake.
- `closeSession()` immediately rejects any in-flight connect Promise rather than waiting for the handshake timeout.
- Live upgrade Promises resolve when `pc.ontrack` fires after renegotiation.

ViewerSession and MonitorSession interfaces are defined in [webrtc-peer.md](webrtc-peer.md) § Session State.

---

## Monitor-Side Session State

Monitor sessions are keyed by `contactId`. The behavioral invariants that govern the connection flows are:

- A `generation` counter on `MonitorSession` increments on every `closeSession()`. Async callbacks capture the generation at start and bail out if it has changed.
- The idle timer resets on every control-channel message received; expiry triggers hangup and session close.

ViewerSession and MonitorSession interfaces are defined in [webrtc-peer.md](webrtc-peer.md) § Session State.

---

## Public API

viewer-peer.ts exposes:
- `connectToMonitor(contactId: string): Promise<void>` — establishes data connection; resolves when controlChannel opens
- `startLiveView(contactId: string, channelId: string): Promise<MediaStream>` — upgrades to live; resolves when tracks arrive
- `closeSession(contactId: string): void` — sends hangup signal, closes pc, clears session state

monitor-peer.ts exposes:
- `ensureConnection(contactId: string): Promise<void>` — accepts incoming offer-request; resolves when data channel is open
- `closeSession(contactId: string): void` — closes the session with a viewer

## Viewer-Initiated Data Connection

```
User clicks "Connect"
  │
  └─ connectToMonitor(contactId)
       │
       ├─ sessions.has(contactId)?  → return (already connected)
       ├─ connectPromises.has(contactId)? → return same Promise (in progress)
       │
       └─ new Promise (stored in connectPromises):
            │
            ├─ sendOfferRequest(mode='data', sessionId)     [Nostr event 1]
            │
            ├─ pc.ondatachannel → 'control' channel arrives
            ├─ controlChannel.onopen → resolve
            ├─ timeout 60s → fail() + closeSession()
            ├─ ICE 'failed'/'closed' → fail()
            └─ ICE 'disconnected' → 8s grace → fail()

  [At monitor — concurrent with viewer waiting]
  handleOfferRequest():
    ├─ close existing viewer session (if any)
    ├─ createPeer()
    ├─ mode='data': no tracks added
    ├─ createDataChannel('control') + createDataChannel('data')
    ├─ createOffer() → setLocalDescription()
    ├─ waitForIceGathering()
    └─ sendOffer(sdp, sessionId)                            [Nostr event 2]

  [Back at viewer]
  handleOffer() on kind 5001 isResponse=true:
    ├─ setRemoteDescription(offer)
    ├─ createAnswer() → setLocalDescription()
    ├─ waitForIceGathering()
    └─ sendAnswer(sdp, sessionId)                           [Nostr event 3]

  [At monitor]
  handleAnswer():
    └─ setRemoteDescription(answer) → ICE completes → channels open

  [At viewer]
  controlChannel.onopen fires → resolve connectPromises entry

  [connectToMonitor resolves]
  ├─ requestChannelList() → data channel query to monitor
  └─ viewerConnection.update({ status: 'online', mode: 'data', channels: [...] })
```

**Total Nostr events: 3**

## Viewer Upgrades to Live (In-Band Renegotiation)

When a data session is already open, upgrading to live avoids a full reconnect. Sending a new offer-request would cost 4 Nostr events (offer-request + offer + answer + hangup of old session). In-band renegotiation costs 2.

```
User clicks "Watch Live" (controlChannel.readyState === 'open')
  │
  └─ startLiveView(contactId, channelId)
       │
       ├─ session.mode = 'live'
       ├─ viewerConnection.update({ status: 'connecting', mode: 'live' })
       │
       └─ new Promise (stored in pendingLiveUpgrades):
            │
            ├─ timeout 30s → reject pendingLiveUpgrades[contactId]
            ├─ controlChannel.send({ type: 'live-request', channelId })
            │
            │  [At monitor — control channel onmessage]
            │  ├─ buildCompositeStream(channelId)
            │  ├─ pc.addTrack(...) per track
            │  ├─ createOffer() → setLocalDescription()
            │  ├─ waitForIceGathering()
            │  └─ sendOffer(sdp, sessionId)               [Nostr event 4]
            │
            ├─ viewer receives kind 5001 isResponse=true
            │  ├─ setRemoteDescription(offer)
            │  ├─ createAnswer() → setLocalDescription()
            │  ├─ waitForIceGathering()
            │  └─ sendAnswer(sdp, sessionId)              [Nostr event 5]
            │
            │  [At monitor]
            │  └─ setRemoteDescription(answer) → tracks flow
            │
            └─ pc.ontrack fires at viewer → resolve pendingLiveUpgrades

  viewerConnection.update({ status: 'online', mode: 'live' })
```

**Total Nostr events: 2 (plus the 3 from the initial data connection)**

## Viewer-Initiated Live Connection (No Prior Data Session)

```
User clicks "Watch Live" (no existing connection)
  │
  └─ startLiveView(contactId, channelId)
       │
       ├─ controlChannel not open → closeSession(contactId)
       └─ connectToMonitor(contactId)  [with mode='live' + channelId in offer-request]

  [Same 3-event handshake as data connection]
  [Monitor receives offer-request with mode='live' + channelId → adds tracks before createOffer()]
  [controlChannel.onopen fires → connectToMonitor resolves]
  [pc.ontrack fires → live tracks available; startLiveView resolves]
```

**Total Nostr events: 3**

## Monitor Idle Timeout

The monitor resets a 120-second timer on every control-channel message. If no message arrives within the window:

```
idleTimer fires:
  ├─ sendHangup(sessionId)
  └─ closeSession(contactId)

Viewer receives kind 5003:
  └─ closeSession(contactId)
```

Either side can initiate hangup. The signal router delivers kind 5003 to both viewer and monitor handlers — each checks its own session map and closes the matching session.

---

## Live Stream Track Selection

When the monitor receives an offer-request with `mode='live'` or a `live-request` on the control channel, it builds a composite `MediaStream` using this priority order:

1. **Active sources override** — set by `RecordingController` via `onActiveSources` callback:
   ```typescript
   const override = channelActiveSources.get(channelId);
   const videoSrcId = override?.videoSourceId ?? channelConfig.videoSourceId;
   ```

2. **Channel configured defaults** — `videoSourceId` / `audioSourceId` from `ChannelConfig`.

3. **All open sources** — if no `channelId` is specified, all tracks from all active streams are composited.

4. **Empty stream** — if no sources are available. The viewer receives no `ontrack` event; live playback shows black.

The `channelActiveSources` map is updated by `RecordingController` when a recording action starts or stops, allowing the recording session to override channel defaults independently of viewer connections.

## Error Handling

### Connection Timeouts

| Phase | Timeout | On expiry |
|-------|---------|-----------|
| Full handshake | 60s | Reject connect Promise, close session |
| ICE gathering (non-trickle) | 5s | Proceed with partial candidates |
| Live upgrade renegotiation | 30s | Reject `pendingLiveUpgrades` Promise |
| Monitor idle (no messages) | 120s | Send hangup, close session |
| ICE disconnected grace | 8s | Close session if still disconnected |

### ICE Failure Modes

ICE state changes drive session cleanup on the viewer side:

```typescript
onIceStateChange(pc, (state) => {
  if (state === 'failed' || state === 'closed') {
    if (!settled) fail(new Error('ICE connection failed — NAT traversal may require a TURN server'));
    else closeSession(contactId);
  } else if (state === 'disconnected') {
    disconnectGraceTimer = setTimeout(() => {
      if (!settled) fail(new Error('ICE disconnected'));
      else closeSession(contactId);
    }, 8_000);
  }
});
```

The 8-second grace window absorbs transient network blips without dropping the session immediately.

### Relay Rate-Limit Retry

If a relay rate-limits a signal during the handshake, the sender retries via the relay selection logic defined in [nostr-client.md](nostr-client.md) § Pattern 3: Relay Selection for Publish.

## Example Workflows

### Workflow 1: Data-Only Connection

```
1. Viewer: sendOfferRequest(mode='data')                    [event 1]
2. Monitor: handleOfferRequest() → createOffer() → sendOffer()  [event 2]
3. Viewer: setRemoteDescription() → createAnswer() → sendAnswer()   [event 3]
4. Monitor: setRemoteDescription() → channels open
5. Viewer: controlChannel.onopen → connected
6. Viewer: requestChannelList() → data channel query → viewerConnection status: online

Total: 3 Nostr events, ~2–5 seconds
```

### Workflow 2: Live Upgrade from Existing Data Session

```
[Data session from Workflow 1 already open]

1. Viewer: controlChannel.send({ type: 'live-request', channelId: 'front-door' })
2. Monitor: buildCompositeStream() → addTrack() → createOffer() → sendOffer()  [event 4]
3. Viewer: setRemoteDescription() → createAnswer() → sendAnswer()              [event 5]
4. Monitor: setRemoteDescription() → media flows
5. Viewer: pc.ontrack fires → pendingLiveUpgrades resolves → status: live

Total additional: 2 Nostr events, ~1–2 seconds
Combined from start: 5 events
```
