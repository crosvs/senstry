# WebRTC Architecture

## Overview

Senstry uses WebRTC for two distinct but intermingled use cases:

1. **Live Streaming** — Monitor broadcasts video+audio media tracks to viewer in real-time
2. **Data Channel** — Viewer requests metadata, coverage maps, and segment blobs from monitor on-demand

Both cases share a single `RTCPeerConnection` per viewer per monitor. The mode (`'live'` or `'data'`) is declared at connection initiation via an `offer-request` signal. Data-only connections explicitly skip media track setup to avoid unnecessary bandwidth.

**Key architectural property:** The handshake is non-trickle, compressing 3 Nostr signal events into the handshake (vs. ~15 with trickle ICE). Live upgrades further compress to 2 events via an in-band renegotiation path.

## Module Responsibilities

| Module | Role | Perspective |
|--------|------|---|
| `peer` | `RTCPeerConnection` factory, ICE gathering helpers | Symmetric (both sides use) |
| `signaling` | Signal send/receive, encryption (ECDH channel keys), TTL + dedup | Symmetric |
| `signal-router` | Single global subscription to all signal kinds (5001–5006, 5010, 5011), routing to handlers; kind 5006 events are routed to RemoteCommandController | Symmetric |
| `viewer-peer` | Viewer session management, Promise-based request API, session state | Viewer side |
| `monitor-peer` | Monitor session management, data channel message server, connection setup | Monitor side |

## Signal Types and Their Flow

### Message Format

All signals are encrypted Nostr events. Each signal type has its own kind; `isResponse` distinguishes initiator from responder within a kind. See `nostr-communication-flow.md` for full per-kind payload types.

```typescript
// Kind 5001 — RTC Session (offer-request / offer)
interface RtcSessionPayload {
  sessionId: string;
  mode?: 'live' | 'data';  // isResponse=false: viewer declares desired mode
  sdp?: string;            // isResponse=true: monitor's SDP offer
  isResponse: boolean;
}

// Kind 5002 — RTC Answer
interface RtcAnswerPayload {
  sessionId: string;
  sdp?: string;   // isResponse=false: viewer's SDP answer
  isResponse: boolean;
}

// Kind 5003 — RTC Hangup
interface RtcHangupPayload {
  sessionId: string;
  isResponse: boolean;
}
```

**Nostr Transmission (all RTC signal kinds):**
- Kinds: 5001–5006, 5010, 5011 (see per-kind sections and nostr-communication-flow.md for payload types)
- Encryption: NIP-44 ChaCha20-Poly1305 over ECDH-derived channel keys
- Pubkey: ECDH channel key (not real identity key)
- `created_at`: Honest timestamp (not randomized)
- Subscription: T+0 only (`since: now`); no history replay in subscribe

**Gift wrap (NIP-59) is not used anywhere in Senstry.** All signals — both during pairing and post-contact — use single-layer NIP-44 encryption over ECDH-derived channel keys. Pre-contact delivery uses the TOTP mailbox (kind 5201), not NIP-59 gift wrap. See `nostr-communication-flow.md` for the full contact model and signal flow.

### Handshake Signal Kinds

#### Kind 5001 isResponse=false — Offer-Request
**Direction:** Viewer → Monitor  
**When:** When viewer initiates connection (either data or live mode)  
**Payload:**
- `sessionId`: UUID generated by viewer
- `mode`: 'data' or 'live' (declares viewer's intent)
- `channelId`: (optional, live only) which channel to composite
- `sourceId`: not used

**What happens at monitor:**
- `handleOfferRequest(privkey, monitorPubkey, msg, viewerPubkey)` receives it
- If mode='live' and streams available, adds media tracks to PC via `buildCompositeStream()`
- Creates 'control' and 'data' data channels
- Creates offer SDP, waits for ICE gathering
- Sends back an `offer` signal (with SDP)
- Resets idle timeout

**Rate limiting:** Data-mode offer-requests are rate-limited to 1 per 5s per viewer to absorb relay replays on startup. Live-mode bypasses this since it's user-initiated.

#### Kind 5001 isResponse=true — Offer (SDP)
**Direction:** Monitor → Viewer (initial, or renegotiation)  
**When:** 
1. Monitor responding to viewer's offer-request with initial SDP
2. Monitor renegotiating after receiving `live-request` on control channel

**Payload:**
- `sessionId`: echoed from offer-request (same session)
- `sdp`: complete Session Description Protocol with all ICE candidates

**What happens at viewer:**
- `handleViewerSignal(msg, fromPubkey)` checks session exists and sessionId matches
- `pc.setRemoteDescription({ type: 'offer', sdp })`
- `pc.createAnswer()` → `pc.setLocalDescription(answer)`
- Waits for ICE gathering to complete
- Sends `answer` signal back with answer SDP

#### Kind 5002 isResponse=false — Answer (SDP)
**Direction:** Viewer → Monitor  
**When:** Viewer responding to monitor's offer (kind 5001 isResponse=true)  
**Payload:**
- `sessionId`: matches the offer's sessionId
- `sdp`: viewer's answer SDP

**What happens at monitor:**
- `handleAnswer(msg, viewerPubkey)` matches session by sessionId
- `pc.setRemoteDescription({ type: 'answer', sdp })`
- ICE candidates from both sides are now known; media/data can flow

#### Kind 5003 isResponse=false — Hangup
**Direction:** Either → Either  
**When:** Explicitly closing a session (idle timeout, user click, error)  
**Payload:**
- `sessionId`: of the session being terminated

**What happens:**
- Monitor receives: `handleHangup()` closes the viewer session
- Viewer receives: `onSignal(contactId, 5003, payload)` → `closeSession(payload.sessionId)`
- Both sides route hangup to both handlers so either side can initiate

### Presence Signal Kinds

#### Kind 5004 isResponse=false — Status Announcement
**Direction:** Either → Either  
**When:** Broadcasting online/offline state, or soliciting a reply  
**Payload:**
- `state`: 'online' or 'offline'
- `isResponse: false`

**Handling:**
- `updatePeerStatus(pubkey, state, createdAt)` updates the peer-status store
- **Auto-reply logic (signal-router.ts):**
  - If `isResponse=false`, age ≤ 15s, and startup grace expired:
    - Reply once per peer per 60s cooldown with kind 5004 `isResponse=true, state: 'online'`
  - Only auto-reply to announcements (isResponse=false), preventing loops
  - Startup grace suppresses replies for 20s after signal router starts (preserves relay budget for WebRTC handshake)

#### Kind 5004 isResponse=true — Status Reply
**Direction:** Either → Either  
**When:** Peer received kind 5004 `isResponse=false` and is confirming online state  
**Payload:**
- `state`: 'online' or 'offline'
- `isResponse: true`

**Handling:**
- Auto-replied immediately with kind 5004 `isResponse=true, state: 'online'` (bypasses startup grace)
- Signal router only auto-replies to `isResponse=false` events — prevents reply loops

Kinds 5005 (Relay Migration) and 5006 (Remote Command) are handled by the signal router (see Module Responsibilities table); their payload structures are defined in `nostr-communication-flow.md`.

## ICE Gathering (Non-trickle)

**Implementation:** `waitForIceGathering(pc, timeoutMs=5000)` in `peer.ts`

```typescript
export function waitForIceGathering(pc: RTCPeerConnection, timeoutMs = 5000): Promise<void> {
  return new Promise<void>((resolve) => {
    if (pc.iceGatheringState === 'complete') { resolve(); return; }
    let timer: ReturnType<typeof setTimeout> | null = null;
    const done = () => { if (timer !== null) { clearTimeout(timer); } pc.removeEventListener(...); resolve(); };
    const handler = () => { if (pc.iceGatheringState === 'complete') done(); };
    timer = setTimeout(done, timeoutMs);  // fallback: proceed after 5s even if STUN fails
    pc.addEventListener('icegatheringstatechange', handler);
  });
}
```

**Benefits:**
- All ICE candidates are embedded in the SDP body
- No trickle means 3 Nostr events per handshake (kind 5001 ×2, kind 5002 ×1) vs. ~15 with trickle
- Simpler Nostr event flow, fits within relay rate limits
- Single round-trip delay (RTT) to get connected

**Cost:**
- 5s timeout if STUN server is unreachable (fallback: proceed with whatever candidates were gathered)
- Browser may defer full ICE gathering if address enumeration is slow; 5s is a reasonable middle ground

**Where it's used:**
1. Monitor in `handleOfferRequest()`: waits after `pc.setLocalDescription(offer)` before sending offer
2. Viewer in `handleViewerSignal()` when processing offer: waits after `pc.setLocalDescription(answer)` before sending answer
3. Monitor in live-upgrade renegotiation: waits after `pc.setLocalDescription(offer)` before sending renegotiation offer

## Session Lifecycle

### Viewer-Initiated Data Connection

```
User clicks "Connect"
  │
  ├─→ connectToMonitor(privkey, viewerPubkey, monitorPubkey)
  │     └─ viewerConnection.update({ status: 'connecting', mode: 'data' })
  │
  └─→ ensureConnection(privkey, viewerPubkey, monitorPubkey, 'data')
      │
      ├─ check existing session + connectPromises → skip if already in progress
      ├─ sendOfferRequest(privkey, viewerPubkey, monitorPubkey, sessionId, 'data')
      │   └─ Nostr signal (via signal-router subscription)
      │
      └─ Promise waits for:
          ├─ pc.ondatachannel event → 'control' channel arrives
          ├─ controlChannel.onopen
          └─ resolve ensureConnection promise
          
          [Meanwhile at monitor]
          handleOfferRequest() → setIdleTimer()
          [Then Nostr event arrives at both]
          createOffer → sendOffer Nostr signal
          [Viewer receives offer]
          handleViewerSignal() → setRemoteDescription → createAnswer → sendAnswer
          [Monitor receives answer]
          handleAnswer() → setRemoteDescription
          [ICE completes, channels become open]
          
          Viewer: controlChannel.onopen fires → resolve promise
          
      └─ connectToMonitor continues:
          ├─ _fetchChannelList(monitorPubkey)  ← queries monitor over RTC
          │   └─ dc.send({ type: 'channel-list-request' })
          │   └─ wait for { type: 'channel-list', channels: [...] }
          │
          └─ viewerConnection.update({ status: 'online', mode: 'data', channels: [...] })

Total Nostr events: 3 (kind 5001 isResponse=false + kind 5001 isResponse=true + kind 5002 isResponse=false)
```

### Viewer Upgrades to Live (In-Band)

```
User clicks "Watch Live" (existing data connection open)
  │
  └─→ startLiveView(privkey, viewerPubkey, monitorPubkey, channelId)
      │
      ├─ Check: existing?.controlChannel?.readyState === 'open'? → YES
      │
      ├─ existing.mode = 'live'
      ├─ viewerConnection.update({ status: 'connecting', mode: 'live' })
      │
      └─ Create pendingLiveUpgrades promise:
          │
          ├─ controlChannel.send({ type: 'live-request', channelId })
          │
          └─ Wait for:
              [Monitor receives live-request on controlChannel.onmessage]
              buildCompositeStream(channelId)
              pc.addTrack(...) for each track
              createOffer → setLocalDescription
              waitForIceGathering()
              sendOffer Nostr signal (renegotiation)
              
              [Viewer receives offer]
              handleViewerSignal() → setRemoteDescription → createAnswer → sendAnswer
              [Monitor receives answer]
              handleAnswer() → setRemoteDescription
              
              [Tracks arrive at viewer via ontrack event]
              pc.ontrack fires → reads session.mode === 'live'
              → remoteStream.set(stream)
              → resolve pendingLiveUpgrades promise

Total Nostr events: 2 (renegotiation offer + answer)
Total vs. full reconnect: saves 1 event (offer-request)
```

### Viewer-Initiated Live Connection (no prior data)

```
User clicks "Watch Live" (no existing connection)
  │
  └─→ startLiveView(privkey, viewerPubkey, monitorPubkey, channelId)
      │
      ├─ Check: existing?.controlChannel?.readyState === 'open'? → NO
      │
      ├─ closeSession(monitorPubkey)  ← clean slate
      └─ ensureConnection(privkey, viewerPubkey, monitorPubkey, 'live', undefined, channelId)
      
      [Same as data connection, but mode='live' + channelId]
      [Monitor receives offer-request with mode='live' → adds tracks]
      [Full 3-event handshake]

Total Nostr events: 3 (kind 5001 isResponse=false + kind 5001 isResponse=true + kind 5002 isResponse=false)
```

### Monitor Idle Timeout

```
Session open, no data channel messages received
  │
  └─ resetIdleTimer(privkey, monitorPubkey, session) [reset on each message]
     └ setTimeout(async () => {
         await sendHangup(privkey, monitorPubkey, viewerPubkey, sessionId)
         closeSession(viewerPubkey)
       }, idleTimeoutMs)  // default 120_000ms

Idle timeout:
  └─ Monitor sends 'hangup' signal
  └─ Viewer receives hangup → closeSession()
```

## Data Channel Protocol

Two independent `RTCDataChannel`s per session:

1. **'control'** — JSON metadata requests/responses, small messages (non-blocking)
2. **'data'** — Binary segment chunk payloads (can be large, chunked)

### Control Channel Message Types

All messages are JSON strings. Sent/received by `handleDataMessage()` on monitor, correlated with pending callbacks in viewer.

#### Request/Response Pairs

| Request | Response | Notes |
|---------|----------|-------|
| `{ type: 'source-list-request' }` | `{ type: 'source-list', sourceIds: [...] }` | List of open source IDs from monitor |
| `{ type: 'channel-list-request' }` | `{ type: 'channel-list', channels: [ChannelConfig, ...] }` | Live ChannelConfigs from monitor |
| `{ type: 'segment-channels-request' }` | `{ type: 'segment-channels', channels: [...] }` | Distinct channel IDs in stored segments |
| `{ type: 'coverage-request', mimePrefix?, channelId? }` | `{ type: 'coverage-map', segments: [[start, end], ...], mimePrefix }` | Coverage intervals |
| `{ type: 'coverage-channels-request', mimePrefix? }` | `{ type: 'coverage-channels', channels: { [channelId]: [[start, end], ...], ... } }` | Per-channel coverage |
| `{ type: 'segment-request', time, mimePrefix?, channelId? }` | `segment-meta` + `segment-chunk`×N or `segment-error` | Fetch segment at timestamp |
| `{ type: 'segment-request-by-id', segmentId }` | `segment-meta-by-id` + `segment-chunk-by-id`×N or `segment-error-by-id` | Fetch by ID |
| `{ type: 'segments-after-request', after, count }` | `{ type: 'segments-after', segments: [SegmentMeta, ...] }` | Metadata for up to 20 after timestamp |
| `{ type: 'segments-before-request', before, count }` | `{ type: 'segments-before', segments: [SegmentMeta, ...] }` | Metadata for up to 20 before timestamp |
| `{ type: 'segments-in-range-request', from, to, limit, order, knownIds, mimePrefix?, channelId? }` | `{ type: 'segments-in-range', segments: [SegmentMeta, ...] }` | Metadata in range, excluding known IDs |

#### Special: live-request (In-Band Renegotiation)

| Request | Response |
|---------|----------|
| `{ type: 'live-request', channelId }` | *(renegotiation offer sent via Nostr)* |

Handled inline in `monitor-peer.ts` `controlDc.onmessage` handler. Does not send a control-channel response; instead triggers WebRTC renegotiation (offer SDP sent via Nostr signal).

### Data Channel Message Types

Segment chunk payloads. Sent only from monitor → viewer.

```json
{
  "type": "segment-chunk",
  "requestTime": 1700000000,
  "startTime": 1699999995,
  "index": 0,
  "total": 8,
  "data": "<base64-encoded 32KB chunk>"
}
```

Or by-ID variant:
```json
{
  "type": "segment-chunk-by-id",
  "segmentId": "abc123...",
  "startTime": 1699999995,
  "index": 0,
  "total": 8,
  "data": "<base64>"
}
```

### Segment Metadata Response

Sent on control channel before chunks:

```json
{
  "type": "segment-meta",
  "requestTime": 1700000000,
  "segmentId": "<canonical-id>",
  "startTime": 1699999995,
  "endTime": 1700000005,
  "mimeType": "video/webm; codecs=vp8",
  "sizeBytes": 245760,
  "originMonitor": "<monitor-pubkey>",
  "contentHash": "<sha256-hex>",
  "channelId": "camera-1"
}
```

**Key fields:**
- `segmentId`: Always the canonical ID (`segment.backupOf ?? segment.segmentId`). Viewer uses this for deduplication and sets `backupOf` if it differs from requested ID.
- `contentHash`: SHA-256 of uncompressed bytes. Viewer verifies after reassembly; rejects on mismatch.
- `originMonitor`: Source device pubkey (for multi-device viewers to filter/tag segments).

### Error Responses

```json
{
  "type": "segment-error",
  "requestTime": 1700000000,
  "reason": "not-stored" | "blob-missing"
}
```

Or by-ID variant:
```json
{
  "type": "segment-error-by-id",
  "segmentId": "abc123...",
  "reason": "not-stored" | "blob-missing"
}
```

### Segment Transfer Flow

1. Viewer sends control-channel request: `{ type: 'segment-request', time }`
2. Monitor finds segment at that time range
3. Monitor sends `segment-meta` on control channel (low latency, no blocking)
4. Monitor streams `segment-chunk` messages on data channel (can be large, chunked)
5. Viewer accumulates chunks by index in `pendingSegments.get(requestTime).chunks`
6. When all chunks received: verify hash → resolve Promise with Blob

**Design rationale:**
- Control channel for metadata (low latency, not blocked by large transfers)
- Data channel for chunks (can pipeline without blocking control messages)
- Correlation by `requestTime` or `segmentId` allows multiple overlapping requests

## Viewer-to-Monitor Request API

All requests in `viewer-peer.ts` follow a Promise pattern:

```typescript
export async function requestCoverageMap(
  privkey: Uint8Array,
  viewerPubkey: string,
  monitorPubkey: string,
  mimePrefix?: string,
  channelId?: string
): Promise<[number, number][]>
```

**Implementation pattern:**
1. Check session exists and control channel is open → throw 'offline'
2. Create pending callback: `pendingCoverage = (segments) => { resolve(segments); }`
3. Send request on control channel
4. Set 5-10s timeout, reject on timeout
5. Monitor receives request, sends response on control channel
6. `handleControlMessage()` matches response by type, calls pending callback
7. Promise resolves with result

**Timeouts per request type:**
- `requestCoverageMap()`: 10s
- `requestSegment()`: 30s (large transfer)
- `requestChannelCoverage()`: 10s
- `requestSegmentsAfter()`: 10s
- `requestSegmentsBefore()`: 10s
- `requestSegmentsInRange()`: 15s (potentially large)
- `requestSourceList()`: 5s
- `requestSegmentChannels()`: 5s

## Monitor-Side Message Handling

In `monitor-peer.ts::handleDataMessage()`:

1. **Metadata queries** (source-list, channel-list, coverage, etc.)
   - Query IDB or in-memory state
   - Send response immediately on control channel

2. **Segment requests**
   - Query IDB for segment metadata
   - Call `getSegmentById()` to retrieve blob + metadata
   - Send metadata on control channel
   - Stream chunks on data channel via `sendSegmentOverDc()`

3. **Viewer chains**
   - If segment already in local IDB (e.g., viewer A fetched it, now serving to viewer B):
   - Send `canonicalSegmentId = segment.backupOf ?? segment.segmentId` so viewer B sets `backupOf` correctly
   - This ensures deduplication works across viewer chains

## Encryption: ECDH Channel Keys

### Derivation

**Channel key derivation:** `deriveChannelKey()` in the crypto module

```typescript
export function deriveChannelKey(sharedSecret: Uint8Array, fromPubkey: string, toPubkey: string): Uint8Array {
  // Derive directional channel keys from ECDH shared secret
  // Both sides independently derive the same keys (deterministic)
  // fromPubkey/toPubkey order determines direction
}
```

**Subscription:** Managed internally by `NostrClient.startSignalRouter(onSignal)`.

The router derives inbound channel pubkeys from all paired devices (one per direction, via `deriveChannelKey`), subscribes T+0 to all signal kinds across all inbound relays, and delivers decrypted payloads to the `onSignal` callback. Callers never manage subscriptions or channel keys directly.

```typescript
// Conceptual subscription the router maintains per paired device:
// { kinds: [5001, 5002, 5003, 5004, 5005, 5006, 5010, 5011], authors: [inboundChannelPubkey], since: now }
```

**Transmission:** `sendSignal()`

```typescript
const sharedSecret = getConversationKey(privkey, toPubkey);
const outboundChannelPrivkey = deriveChannelKey(sharedSecret, fromPubkey, toPubkey);
const outboundChannelPubkey = getPublicKey(outboundChannelPrivkey);

const plaintext = JSON.stringify(msg);
const content = encryptSignalContent(plaintext, outboundChannelPrivkey, outboundChannelPubkey);

const event = finalizeEvent({
  kind: kind,  // 5001–5006, 5010, 5011 depending on signal type
  created_at: Math.floor(Date.now() / 1000),  // honest timestamp (not randomized)
  tags: [],
  content
}, outboundChannelPrivkey);
```

### Benefits

- **No key exchange:** Channel keys are derived from already-known shared secret (real ECDH)
- **Honest timestamps:** No randomization; `since` filters become reliable, subscription window shrinks to ~1h
- **Single-layer encryption:** One NIP-44 layer over ECDH-derived channel keys
- **Backward compatible:** No re-pairing needed; all existing paired devices benefit automatically

### Implementation Detail

Each direction has its own channel key:
- **Monitor → Viewer:** Signed with `deriveChannelKey(sharedSecret, monitorPubkey, viewerPubkey)`
- **Viewer → Monitor:** Signed with `deriveChannelKey(sharedSecret, viewerPubkey, monitorPubkey)`

Receiver derives the sender's outbound key and verifies it matches the event's pubkey before decrypting.

## Session State Management

### Viewer Side

```typescript
interface ViewerSession {
  pc: RTCPeerConnection;
  monitorPubkey: string;
  sessionId: string;
  controlChannel: RTCDataChannel | null;
  dataChannel: RTCDataChannel | null;
  mode: 'live' | 'data';
}

const sessions = new Map<monitorPubkey, ViewerSession>();
const connectPromises = new Map<monitorPubkey, Promise<void>>();
const pendingLiveUpgrades = new Map<monitorPubkey, { resolve, reject }>();
const connectAborts = new Map<monitorPubkey, () => void>();
```

**Key invariants:**
- One session per monitor pubkey
- `connectPromises` prevents duplicate concurrent connections to same monitor
- `pendingLiveUpgrades` tracks in-flight upgrade Promise; resolved when ontrack fires after renegotiation
- `connectAborts` allows force-close to reject in-flight connect promise immediately

### Monitor Side

```typescript
interface MonitorSession {
  pc: RTCPeerConnection;
  viewerPubkey: string;
  sessionId: string;
  controlChannel: RTCDataChannel | null;
  dataChannel: RTCDataChannel | null;
  idleTimer: ReturnType<typeof setTimeout> | null;
  generation: number;
}

const sessions = new Map<viewerPubkey, MonitorSession>();
const globalGeneration = number;
```

**Key invariants:**
- One session per viewer pubkey
- `generation` tracks connection version (incremented on closeSession); allows stale signal handlers to ignore outdated work
- `idleTimer` resets on every control-channel message; fires hangup after timeout
- Rate-limit map: `offerRequestTimes: Map<viewerPubkey, timestamp>` tracks data-mode offer-request spam

### Cross-Role Coordination

**Viewer → Monitor:**
- Viewer stores sessions by `monitorPubkey`
- Viewer identifies monitor by pubkey in all signals

**Monitor → Viewer:**
- Monitor stores sessions by `viewerPubkey`
- Monitor identifies viewer by pubkey in all signals (source of offer-request signal)

**Both sides match sessions by `sessionId`** (UUID generated by viewer, echoed in all subsequent signals).

## Error Handling & Recovery

### Connection Timeouts

- **Initial connection:** 60s timeout from `ensureConnection()` promise
- **Idle timeout (monitor):** 120s (configurable via `setIdleTimeout()`)
- **ICE gathering:** 5s fallback (proceeds even if STUN fails)
- **Live upgrade:** 30s timeout for renegotiation to complete

### ICE Failure Modes

```typescript
onIceStateChange(pc, (state) => {
  if (state === 'failed' || state === 'closed') {
    if (!settled) fail(new Error('ICE connection failed — NAT traversal may require a TURN server'));
    else closeSession(monitorPubkey);  // post-connection drop
  } else if (state === 'disconnected') {
    if (disconnectGraceTimer === null) {
      disconnectGraceTimer = setTimeout(() => {
        if (!settled) fail(new Error('ICE disconnected'));
        else closeSession(monitorPubkey);
      }, 8_000);  // 8s grace before failing transient disconnects
    }
  }
});
```

**User-visible errors:**
- "Connection timed out — check that the monitor has 'Accept viewer connections' enabled"
- "ICE connection failed — NAT traversal may require a TURN server"
- "Relay error: ..." (from publish failures)

### Relay Rate-Limit Retry

**Monitor sending offer** (has two retryable events):

```typescript
const OFFER_RETRY_DELAYS_MS = [8_000, 15_000];
for (let attempt = 0; attempt <= OFFER_RETRY_DELAYS_MS.length; attempt++) {
  try {
    await sendOffer(...);
    break;
  } catch (e) {
    if (e.message.includes('rate-limited')) {
      await delay(OFFER_RETRY_DELAYS_MS[attempt]);
    } else {
      throw e;
    }
  }
}
```

**Viewer sending answer** (same retry pattern):

```typescript
const ANSWER_RETRY_DELAYS_MS = [8_000, 15_000];
for (let attempt = 0; attempt <= ANSWER_RETRY_DELAYS_MS.length; attempt++) {
  try {
    await sendAnswer(...);
    break;
  } catch (e) {
    if (e.message.includes('rate-limited')) {
      await delay(ANSWER_RETRY_DELAYS_MS[attempt]);
    } else {
      throw e;
    }
  }
}
```

Retries at 8s, 15s, then give up.

## Live Stream Track Selection

When monitor receives `offer-request` with `mode='live'` or `live-request` on control channel:

1. **If channelId specified:**
   ```typescript
   const override = channelActiveSources.get(channelId);
   const videoSrcId = override?.videoSourceId ?? channelConfig.videoSourceId;
   const audioSrcId = override?.audioSourceId ?? channelConfig.audioSourceId;
   ```
   - First check: active sources from `RecordAction` (pushed by `SentrySection` when recording)
   - Fallback: channel's configured defaults
   - Result: composite stream from selected video+audio sources

2. **If channelId not specified:**
   ```typescript
   // Composite all open sources
   for (const stream of activeStreams.values()) {
     for (const track of stream.getTracks()) composite.addTrack(t);
   }
   ```
   - All audio tracks from all sources mixed into single stream
   - All video tracks (browser will composite or use first depending on sender side)

3. **If no sources are available:**
   - Empty MediaStream (PC has no tracks)
   - Viewer receives no ontrack event; live playback shows black

**The override mechanism (`channelActiveSources`):**
- Set by `RecordingController` via the `onActiveSources` callback when recording starts/stops
- Map from `channelId` to `{ videoSourceId?, audioSourceId? }`
- Allows recording session to override channel defaults (e.g., "record from camera while viewer watches from doorbell sensor")

## Viewer Chain Support

When a viewer re-serves segments to another viewer:

```typescript
// Monitor serving to Viewer A
sendSegmentOverDc(controlDc, dataDc, segment, { requestTime })
// segment.segmentId = "abc123"
// segment.backupOf = null (original monitor)
// → sends segmentId: "abc123"

// Viewer A receives, stores in IDB
// viewerConnection.monitorPubkey = monitorPubkey
// Viewer A then serves to Viewer B
segment = await getSegmentById("abc123")  // from Viewer A's IDB
sendSegmentOverDc(controlDc, dataDc, segment, { requestTime })
// segment.backupOf = null (original)
// → sends segmentId: "abc123" (canonical ID from root monitor)

// Viewer B deduplicates against "abc123"
// both viewers use same dedup key
```

**Implementation:** `segmentId: segment.backupOf ?? segment.segmentId` is always sent so downstream viewers know the canonical ID.

## Summary

The WebRTC implementation is a pragmatic, non-trickle-ICE design optimized for:
- **Minimal Nostr load:** 3 events per handshake, 2 for live upgrades
- **Simple implementation:** No event ordering complexity, no incomplete offer handling
- **Data channel versatility:** Request/response API for metadata and segment transfers
- **In-band optimization:** Live upgrades via renegotiation without extra offer-request event

The ECDH channel-key encryption provides honest timestamps and shrinks subscription window to ~1h. The signal router handles multi-role (both monitor and viewer on same device) and presence protocol with loop prevention.
